# Сборка и публикация релизов на GitHub

## Что собирается

Интерфейс содержит JavaScript, shell-скрипт и файлы конфигурации. В Makefile
указано `LUCI_PKGARCH:=all`, поэтому для всех процессоров и target достаточно
двух пакетов:

```text
luci-app-byedpi-1.0.0-r1-openwrt-24.10-all.ipk
luci-app-byedpi-1.0.0-r1-openwrt-25.12-all.apk
```

Две сборки нужны из-за разных версий OpenWrt и форматов пакетов.
CI собирает только `luci-app-byedpi`. При отсутствии основного сервиса
установщик предлагает установить его из релизов DPITrickster после согласия
пользователя. В CI и зависимостях пакета основной сервис не добавляется.

Для каждой ветки автоматически выбирается SDK последнего стабильного
patch-релиза из [официального каталога OpenWrt](https://downloads.openwrt.org/releases/).
Достаточно одного SDK x86/64 на ветку: это инструмент сборки, а итоговый
пакет с архитектурой `all` подходит также для ARM, MIPS и других процессоров.
SDK проверяется по SHA-256 перед распаковкой. Точная версия SDK записывается
в `build-info.json` релиза.

## Первоначальная настройка GitHub

1. Загрузите весь проект в свой GitHub-репозиторий, включая `.github/workflows`.
2. В **Settings → Actions → General** разрешите Actions и официальные
   `actions/*`. Для fork подтвердите включение Actions.
3. Workflow должен находиться в основной ветке (`main` или `master`),
   чтобы появилась кнопка **Run workflow**.
4. Секреты и PAT не нужны: используется штатный `GITHUB_TOKEN`.
   Только задача публикации запрашивает `contents: write`. Политика организации
   должна разрешать создание релизов этим токеном.
5. Для установки через анонимный `/releases/latest/download/` используйте
   публичный репозиторий и обычный опубликованный релиз.

Подробнее: [ручной запуск workflow в GitHub](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).

## Запуск релиза

1. Укажите версию в `luci-app-byedpi/Makefile`, например
   `PKG_VERSION:=1.0.0` и `PKG_RELEASE:=1`, и загрузите изменения в GitHub.
2. Откройте **Actions → Build and publish release → Run workflow**.
3. Выберите ветку с нужным кодом и заполните единственное поле:
   **release_tag = v1.0.0**. Основная версия должна совпадать с `PKG_VERSION`.
   Также допустим суффикс ревизии из `PKG_RELEASE`, например `v1.0.0-r2`.
4. Нажмите **Run workflow**. Запустятся проверки и две сборки.
5. После их успеха релиз появится в **Releases**. В нём будут `.ipk`, `.apk`,
   `packages.tsv`, `build-info.json` и `SHA256SUMS`.

Если тег ещё не существует, он создаётся на коммите запуска. Существующий
тег должен указывать на тот же коммит. Workflow сначала создаёт draft,
загружает все файлы и затем публикует релиз. При ошибке одной из двух сборок
публикация не выполняется.

Альтернативный запуск — push тега после обновления версии и исходников:

```sh
git tag v1.0.0
git push origin v1.0.0
```

Или через GitHub CLI:

```sh
gh workflow run release.yml -f release_tag=v1.0.0
```

Для следующего релиза увеличьте `PKG_VERSION`, сбросьте `PKG_RELEASE` до 1
и создайте новый тег.

### Повторный выпуск с той же версией

Можно автоматизировать увеличение ревизии, коммит и создание тега.
Для этого на компьютере разработчика нужен Python 3. Один раз выполните
в репозитории:

```sh
git config --local alias.next '!python3 scripts/git-next.py'
```

После обычного коммита с изменениями запустите:

```sh
git next
```

Команда увеличит `PKG_RELEASE` на 1, создаст коммит `build: bump version`
и тег с новой ревизией. Например, при `PKG_VERSION:=0.0.1` и
`PKG_RELEASE:=2` получится тег `v0.0.1-r3`. Изменения должны быть заранее
закоммичены; при незакоммиченных или новых неотслеживаемых файлах команда
остановится. Существующий тег не перезаписывается.

Отправка на GitHub выполняется отдельно. `git next` выведет готовую команду,
которая отправляет текущую ветку и только созданный тег, например:

```sh
git push --atomic origin HEAD refs/tags/v0.0.1-r3
```

Отправка тега автоматически запускает сборку и публикацию релиза.
Без настройки алиаса можно выполнить `python3 scripts/git-next.py`.
Если создание коммита завершится ошибкой, изменение ревизии останется
для исправления и ручного завершения коммита и создания тега.

При ручном выпуске выполняются те же шаги:

Чтобы выпустить `0.0.1-r2` после `0.0.1-r1`, оставьте основную версию
и увеличьте ревизию в `luci-app-byedpi/Makefile`:

```make
PKG_VERSION:=0.0.1
PKG_RELEASE:=2
```

Загрузите коммит с изменениями в GitHub и запустите **Build and publish release**
на этой ветке с **release_tag = v0.0.1-r2**. Либо отправьте новый тег:

```sh
git tag v0.0.1-r2
git push origin v0.0.1-r2
```

Пакеты получат имена `luci-app-byedpi-0.0.1-r2-openwrt-24.10-all.ipk`
и `luci-app-byedpi-0.0.1-r2-openwrt-25.12-all.apk`. Число после `-r`
должно совпадать с `PKG_RELEASE`. Для следующей ревизии используйте `3`
и новый тег `v0.0.1-r3`. Старые теги и опубликованные релизы менять не нужно.
Теги без суффикса, например `v0.0.1`, по-прежнему поддерживаются.

Обычные push и pull request запускают
**Check LuCI package**, который собирает те же два пакета и сохраняет их
в Artifacts без публикации релиза.

## Установка на роутере

Готовая команда для установки и обновления находится в README.
Установщик `install.sh` находится в корне репозитория и загружается из `main`.
Пакеты и их контрольные суммы он получает из Releases. Пример:

```sh
sh <(wget -q -O - https://raw.githubusercontent.com/qb60/luci-app-byedpi/main/install.sh)
```

Выполните команду от root. Если ByeDPI отсутствует, подтвердите его установку
ответом `y` на вопрос `[y/N]`. Enter или отказ отменяют установку.
Если сервис уже установлен, скрипт проверит доступную версию и предложит
обновление при необходимости. При отказе или Enter будет установлен только
интерфейс. Для повторной проверки обновлений используйте ту же команду.

Архитектуру и target указывать не нужно. Установщик определяет стабильную
ветку OpenWrt, проверяет наличие соответствующего пакетного менеджера
и основного сервиса, выбирает универсальный пакет и сверяет SHA-256. При
согласии установить основной сервис его машинный пакет выбирается по точной
архитектуре из стабильного нативного релиза для 24.10 или 25.12, без generic
и prerelease. Для разбора GitHub API при необходимости устанавливается
стандартный пакет jsonfilter. При первичной установке без подходящего пакета
или ошибке установки/
подтверждённого обновления ByeDPI интерфейс не устанавливается. Если проверка
обновлений уже установленного сервиса недоступна, установка интерфейса
продолжается с текущим ByeDPI.
Любая стабильная patch-версия внутри ветки использует один и тот же пакет.
SNAPSHOT и release candidate автоматически не устанавливаются.

Для установки конкретного релиза передайте тег текущему установщику:

```sh
sh <(wget -q -O - https://raw.githubusercontent.com/qb60/luci-app-byedpi/main/install.sh) qb60/luci-app-byedpi v0.0.1-r2
```

Нужны root, доступ к GitHub по HTTPS, `wget` или `curl`, `sha256sum` и рабочие
официальные package feeds для установки зависимостей LuCI.
Для APK из собственного SDK используется `--allow-untrusted`: контрольная
сумма из HTTPS-релиза не является подписью дистрибутива OpenWrt.

Установленная версия читается из метаданных пакетного менеджера и
сравнивается с доступной через `opkg compare-versions` или `apk version -t`,
включая ревизию пакета. Переустановка той же версии и понижение версии
автоматически не предлагаются. При неизвестной установленной версии
проверка обновления ByeDPI пропускается. Для необязательного обновления
отсутствие терминала считается отсутствием согласия: продолжается только
установка интерфейса. После подтверждённого обновления проверяется, что
пакетный менеджер действительно установил выбранную версию.

Существующая конфигурация ByeDPI сохраняется и восстанавливается после
установки основного пакета, в том числе при ошибке пакетного менеджера.
Если восстановление не удастся, установщик оставляет резервную копию и сообщает
её путь. Скрипт не вызывает `start` или `enable` для ByeDPI; поведение установки
самого пакета остаётся штатным для OpenWrt. Перезапускается rpcd для загрузки
обработчика. После установки откройте **Services → ByeDPI** и настройте сервис.

SHA-256 основного пакета проверяется по digest GitHub API, если он предоставлен.
Для релизов без digest используется HTTPS-загрузка с GitHub. Установка
отсутствующего сервиса требует интерактивного подтверждения из терминала.

## Если запуск завершился ошибкой

- Посмотрите первый ошибочный шаг в Actions; вывод SDK находится в логе.
- Для временного сбоя используйте **Re-run failed jobs**.
- Успешные сборки доступны в **Actions → запуск → Artifacts**.
- Если загрузка релиза оборвалась после создания draft, удалите этот
  незавершённый draft в Releases и повторите публикацию. Workflow не
  перезаписывает существующие релизы автоматически.
- Для исправлений опубликованного кода используйте новую версию и новый тег.

Для обновления только установщика достаточно изменить корневой `install.sh`
и отправить коммит в `main`. Увеличивать `PKG_RELEASE`, ставить тег и пересобирать
пакеты не нужно. Workflow **Check installer** выполнит проверки без SDK-сборки.
При следующем запуске команды из README пользователь получит новый скрипт
и пакеты из последнего опубликованного релиза.

## Локальные проверки

```sh
python3 tests/release.py
bash -n scripts/build-package.sh
busybox ash -n install.sh
actionlint
```

Тесты используют фикстуры SDK и mock-команды роутера. Реальные SDK-сборки,
GitHub Releases и установку на устройстве проверяют отдельно.
